Behind the scenes

How this site is built

I originally built this site to force myself to learn Kubernetes. That worked, but a cluster is a lot to run for a personal site. So I'm rebuilding the hosting around containers on Azure, using the services and practices I most want to know well. This page is honest about what's finished and what's still a plan.

Where it started

The first version was an ASP.NET Core application in a Docker container, deployed to a Kubernetes cluster with Helm charts and an Nginx ingress, and released through Azure DevOps pipelines. It taught me a great deal about how those pieces fit together.

It also showed me the cost. A small always-on cluster needs patching, monitoring, and money every month, and for a handful of web pages that's far more than the job needs. Kubernetes is a tool I'm still learning, and I'd rather say so than pretend otherwise.

Where it is now

A status board, so you can see what's real.

  • DoneA fresh, accessible front end.

    Plain HTML and CSS with no front-end framework and no build step. It's built with keyboard use, screen readers, and reduced-motion settings in mind, and it loads quickly.

  • DoneCurrent runtime.

    The site runs on ASP.NET Core 10, upgraded from .NET Core 3.1.

  • DoneOne source for my resume.

    The resume files are maintained in one folder and copied into the site automatically by the build, so the site never serves a stale copy.

  • NextContainerize it.

    A multi-stage Dockerfile that builds the site and produces a small runtime image.

  • NextAzure Container Registry and Azure Container Apps.

    Store the image in a registry and run it on Container Apps: HTTPS, a custom domain, and scale-to-zero so it costs almost nothing when nobody is visiting.

  • NextInfrastructure as code with Bicep.

    Every Azure resource defined in code, so the whole environment can be rebuilt, or torn down, from a repository.

  • NextA build and release pipeline.

    A YAML pipeline that builds the image, scans it for vulnerabilities, pushes it to the registry, and deploys it on every change. The source code and its history (back to 2020) also need to move from Azure DevOps Git to GitHub.

  • LaterManaged identity and Key Vault.

    No passwords in code: the site authenticates to other Azure services with its own identity, and any secrets live in Key Vault.

  • LaterMonitoring.

    Application Insights with a KQL dashboard for availability, errors, and performance.

  • LaterA real contact form.

    The old form depended on PHP, which doesn't run here. The replacement would be an Azure Function that queues messages through Service Bus and emails me.

  • LaterAn "Ask Glenn" assistant.

    A chat box that answers questions about my experience using vector search over my resume and project write-ups (Cosmos DB or PostgreSQL with pgvector), with Redis for caching and rate limits and a firm spending cap.

The target design

Solid outlines are in place; dashed outlines are planned.

The contact form and the assistant are separate add-ons to the site, and the last pieces I plan to build. The assistant will only go live once spending limits are in place.

Why these choices

  • Container Apps instead of Kubernetes. It runs the same kind of container with a fraction of the operational work, and it can scale to zero. A site with a handful of visitors shouldn't pay for an idle cluster.
  • Bicep for everything. If it isn't in code, it can't be reviewed, repeated, or safely deleted.
  • Scanning in the pipeline. Security checks that fail the build keep problems from shipping. It's the same habit I use at work.
  • Managed identity, not passwords. The fewer secrets there are, the fewer can leak.
  • Monitoring from day one. You can't run what you can't see.

It's also my study project for Microsoft's AI-200 exam (Azure AI Cloud Developer): containers, data services, messaging, and security and monitoring are all on that list, and building something real is the best way I know to learn them.
